## TL;DR

- **Normalization**: Splitting data into multiple tables to eliminate duplicate data. Improves write speed and data integrity, but requires complex `JOIN`s for reads.
- **Denormalization**: Intentionally duplicating data across tables to avoid `JOIN`s. Improves read speed, but makes writes slower and risks data inconsistencies.

## Normalization (The Normal Forms)

Normalization follows strict rules (Normal Forms) to organize data:

1. **1NF (First Normal Form)**: Every column must contain atomic (indivisible) values. No comma-separated lists in a single column.
2. **2NF (Second Normal Form)**: Must be in 1NF. All non-key columns must depend on the *entire* primary key (only relevant for composite keys).
3. **3NF (Third Normal Form)**: Must be in 2NF. No transitive dependencies. A non-key column cannot depend on another non-key column. (e.g., Moving `country` and `currency` into a separate `Countries` table instead of repeating them in `Users`).

## Denormalization

Why would we intentionally break the rules of 3NF? **Performance**.

At massive scale, joining 5 massive tables across millions of rows takes too long. By copying the `user_name` directly into the `Orders` table, we can fetch all order details in a single, blazing-fast read operation.

## Interview Questions

### If Denormalization is so fast for reads, why not always use it?
Because of **Write Anomalies**. If Alice changes her name to "Alicia", a Normalized DB only has to update exactly *one* row in the `Users` table. A Denormalized DB must find and update every single order Alice has ever placed to keep the `user_name` column accurate. If the update fails halfway, the database is inconsistent.

### What is a Star Schema?
A heavily denormalized database structure used in Data Warehouses (OLAP) for analytics. It consists of a central "Fact" table (e.g., Sales) surrounded by denormalized "Dimension" tables (e.g., Time, Store, Product). It is optimized for massive read-heavy aggregations.

## Remember

> **Normalize until it hurts, denormalize until it works.** Start with a perfectly normalized (3NF) database. Only denormalize specific tables when read performance becomes an actual bottleneck.
