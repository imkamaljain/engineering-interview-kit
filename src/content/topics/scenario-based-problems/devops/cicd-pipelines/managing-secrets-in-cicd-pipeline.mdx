## Fast Revision (10-Second Recall)
- **The Cardinal Sins of CI/CD Secrets:**
- 1. Hardcoding secrets in `.env`, Dockerfiles, or Git repos.
- 2. Storing long-lived permanent AWS Access Keys (`AKIA...`) in CI runner secrets.
- 3. Printing secrets in CI console logs.
- **The Modern Standard: OpenID Connect (OIDC) & Short-Lived Tokens:**
- Instead of saving static AWS credentials in GitHub Actions, GitHub assumes an AWS IAM Role via OIDC. AWS validates the cryptographic JWT token and returns a temporary STS credential valid for 1 hour!
- **Secret Management Stack:** HashiCorp Vault / AWS Secrets Manager + External Secrets Operator (ESO) + Pre-commit secret scanning (TruffleHog).

## The 30-Second Spoken Script
"Managing secrets in CI/CD requires a zero-trust approach where permanent, long-lived credentials are completely eliminated in favor of ephemeral, short-lived tokens and centralized secret stores.

I implement four core security practices:

First, Eliminate Permanent Cloud Keys using OpenID Connect (OIDC).
Instead of generating static AWS Access Keys and storing them in GitHub Actions repository secrets, we configure OIDC federation between GitHub Actions and AWS IAM. When a pipeline runs, GitHub issues a short-lived OIDC JSON Web Token. AWS IAM verifies this token, confirms the repository and branch matches our IAM trust policy, and grants a temporary STS token valid for only 15 minutes. There are zero permanent credentials stored anywhere in CI.

Second, Dynamic Secret Injection via HashiCorp Vault or AWS Secrets Manager.
Application secrets (database passwords, Stripe keys) are never stored in CI manifests. We use HashiCorp Vault or the Kubernetes External Secrets Operator (ESO). The deployment pipeline only references secret keys; the External Secrets Operator running inside the production Kubernetes cluster pulls the decrypted secrets directly from Vault into memory-backed Kubernetes Secrets at runtime.

Third, Masking and Log Sanitization.
CI runners must automatically mask all registered secrets, ensuring that if a script accidentally echoes an environment variable, the CI log displays '***' rather than the plaintext value.

Fourth, Shift-Left Secret Scanning.
We integrate TruffleHog and GitGuardian in both pre-commit hooks and CI pull request gates. If any developer attempts to commit an API key, private key, or password, the commit is immediately rejected before it reaches remote history."

## Scenario / Problem Context
Hardcoded secrets in repositories or unrotated cloud credentials in CI runners are the #1 attack vector for cloud security breaches. The interviewer assesses your understanding of modern DevSecOps, secret lifecycle management, and short-lived credentials.

## Deep-Dive Analysis & Root Causes

| Approach | SecurityLevel | Drawbacks |
| --- | --- | --- |
| Static AWS Access Keys in CI | Vulnerable | Never expires; if leaked, attacker has persistent access; requires manual rotation
OIDC Federation (Recommended) | Enterprise Zero-Trust | Tokens expire in 15 minutes; scoped strictly to repository, branch, and environment
External Secrets Operator (ESO) | High | Decouples CI from secrets entirely; secrets injected directly inside cluster
Pre-Commit Secret Scanning | Preventative | Catches leaks locally before Git history is contaminated |

## Prevention & Senior Best Practices
- **Mandate OIDC for All Cloud Providers:** Eliminate static service account keys in GitHub Actions, GitLab CI, and CircleCI; use OIDC for AWS, GCP, and Azure.
- **Use Secret Scanning in PR Gates:** Integrate TruffleHog or GitHub Secret Scanning with push protection enabled.
- **Enforce Automated Secret Rotation:** Configure AWS Secrets Manager to rotate database credentials every 30 days automatically.
