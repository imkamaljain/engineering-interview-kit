## Scenario

> **How would you identify whether API latency is caused by application code, database queries, or network issues?**

When users report latency, junior developers often guess by tweaking application code or adding random indexes. Senior engineers use **mathematical decomposition of the request lifecycle** to isolate the exact tier causing the delay.


## Fast Revision (10-Second Recall)

- **The Measurement Formula:** $\text{Total Latency} = \text{Network (DNS + TCP + TLS + Transit)} + \text{Gateway Queue} + \text{App Compute} + \text{Database I/O} + \text{Payload Transfer}$.
- **Top 3 Diagnostic Signals:**
  1. **Network vs Server:** Compare client-side **Time To First Byte (TTFB)** against server-side request processing duration. Large delta = Network / Load Balancer delay.
  2. **Database vs App:** Check **Distributed Traces (APM)**: Compare database span time vs application CPU compute span time.
  3. **Network Transit / Ingress:** Check TCP retransmissions, packet loss, and ingress proxy queue wait time (`nginx` `$request_time` vs `$upstream_response_time`).
- **Key Tools:** APM Waterfall (OpenTelemetry/Datadog), `curl -w` network timing, NGINX access logs (`$upstream_response_time`), `tcpdump` / `mtr`.


## The 30-Second Spoken Script

If asked this in an interview, deliver this structured response:

> *I isolate latency by decomposing the request lifecycle into three measurable boundaries: client-to-gateway network transit, application execution time, and database query time.*
>
> *First, I compare the client-measured TTFB against the ingress proxy log. If the client experiences 2 seconds, but the NGINX `$upstream_response_time` reports only 80ms, the bottleneck is external network transit, DNS, or client packet loss.*
>
> *If the reverse proxy shows high upstream response time, the delay is inside the infrastructure. I then check our APM distributed trace.*
>
> *The trace breaks the request into child spans. If the database span accounts for 85% of total duration, the bottleneck is SQL execution, locking, or connection pooling. If the database returns in 10ms, but total span is 1,500ms, the bottleneck is application compute, CPU throttling, or event loop blocking.*

### 1. Step 1: Network vs Server Latency (The Gateway Delta)
In your reverse proxy (NGINX / Envoy / ALB), check two key metrics:
- `$request_time`: Full time from first client byte received until the last byte sent back.
- `$upstream_response_time`: Time taken by the backend application to process and return the response.

$$\Delta = \text{Request Time} - \text{Upstream Response Time}$$

- If $\Delta \approx 0\text{ms}$ and upstream time is high $\rightarrow$ **Application or Database issue**.
- If $\Delta$ is several seconds $\rightarrow$ **Slow client connection, high network transit, or large payload download**.

### 2. Step 2: Application Code vs Database (Trace Span Ratio)
Open the APM trace (Datadog/New Relic) and calculate the ratio:
- $\text{DB Ratio} = \frac{\sum \text{DB Spans}}{\text{Total Trace Duration}}$
- If $\text{DB Ratio} > 70\% \rightarrow$ **Database bottleneck**.
- If $\text{DB Ratio} < 20\%$ and total time is high $\rightarrow$ **Application bottleneck** (CPU profiling, garbage collection, event loop stall).


## Root Causes & Solutions Matrix

| Tier | Diagnostic Signature | Typical Root Cause | Actionable Fix |
| :--- | :--- | :--- | :--- |
| **Network** | High TTFB on client, but fast NGINX upstream time; high TCP retransmissions. | Cross-region routing, MTU misconfiguration, packet loss. | Deploy multi-region CDN, enable HTTP/3, co-locate services in same VPC. |
| **Gateway Queue** | High NGINX request time before forwarding to upstream. | Connection pool to backend exhausted; worker process limits reached. | Increase upstream `keepalive` connections in reverse proxy. |
| **Application** | Low DB query time, high CPU utilization, event loop lag > 100ms. | Synchronous CPU computation, JSON serialization, unhandled promise loop. | Run CPU flamegraph, move heavy compute to worker threads, stream responses. |
| **Database** | High DB span in APM; `pg_stat_activity` shows long active queries. | Missing index, lock contention, full table scans. | Add targeted index, tune autovacuum, optimize SQL query. |


## Practical Debugging Commands & Code

### 1. Granular Latency Profiling with `curl`
Execute a timed HTTP request to break down DNS, TLS, TCP, and server processing times:
```bash
curl -w "DNS: %{time_namelookup}s\n\
TCP Handshake: %{time_connect}s\n\
TLS Negotiation: %{time_appconnect}s\n\
Pre-Transfer: %{time_pretransfer}s\n\
TTFB (Server Processing): %{time_starttransfer}s\n\
Total Duration: %{time_total}s\n" \
-o /dev/null -s "https://api.yourdomain.com/v1/users"
```

### 2. NGINX Access Log Latency Analysis
Configure NGINX logs to output both client and upstream timing:
```nginx
log_format detailed_timing '$remote_addr - $remote_user [$time_local] '
                          '"$request" $status $body_bytes_sent '
                          'rt=$request_time uct="$upstream_connect_time" '
                          'uht="$upstream_header_time" urt="$upstream_response_time"';
```

### 3. Measure Node.js Event Loop Lag
Detect when application code blocks asynchronous I/O handling:
```typescript
import { monitorEventLoopDelay } from 'perf_hooks';

const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

setInterval(() => {
  const p99LagMs = histogram.percentile(99) / 1e6;
  if (p99LagMs > 50) {
    console.warn(`[WARNING] High Event Loop Lag: ${p99LagMs.toFixed(2)}ms`);
  }
  histogram.reset();
}, 5000);
```


## Prevention & Senior Best Practices

1. **Implement OpenTelemetry Across All Boundaries:** Trace every request seamlessly from frontend client to gateway, backend services, and database.
2. **Alert on Synthetic Probes (Blackbox Monitoring):** Run automated synthetic requests from multiple global regions every 60 seconds to detect network routing degradation early.
3. **Establish Clear Latency Budgets:** Set strict architectural budgets: Gateway < 10ms, Application logic < 40ms, Database queries < 50ms.
