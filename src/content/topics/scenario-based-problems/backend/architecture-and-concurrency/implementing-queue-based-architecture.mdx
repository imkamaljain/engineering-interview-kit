## Scenario

> **How would you implement a queue-based architecture?**

As backend systems scale, synchronous communication breaks down under bursty traffic: if 10,000 users upload files simultaneously, synchronous processing exhausts memory and database connections. The interviewer expects an architectural design using the **Producer-Consumer pattern with message durability, backpressure regulation, prefetch limits, and worker autoscaling**.


## Fast Revision (10-Second Recall)

- **The Core Architecture:**
  - **Producers (API Servers):** Validate payload, publish message to broker, return instant `202 Accepted`.
  - **Message Broker (Redis/RabbitMQ/SQS):** Buffers messages durably on disk/memory.
  - **Consumers (Worker Nodes):** Poll/pull messages, process compute, send explicit `ACK` (acknowledgment) upon completion.
- **Top 4 Production Safeguards:**
  1. **At-Least-Once Delivery & Idempotency:** Consumers MUST be idempotent; duplicate message delivery is guaranteed in distributed networks.
  2. **Prefetch Count (Backpressure):** Limit how many unacknowledged messages a worker can buffer (e.g., `prefetch = 10`) so a single worker doesn't hoard work and crash.
  3. **Dead-Letter Queues (DLQ):** Route messages that fail 3 consecutive times to a separate quarantine queue for human investigation.
  4. **Worker Autoscaling (KEDA):** Scale consumer pods horizontally based on **Queue Backlog Depth**, not CPU utilization.
- **Key Tools:** BullMQ (Redis), RabbitMQ, AWS SQS, KEDA (Kubernetes Event-driven Autoscaling).


## The 30-Second Spoken Script

If asked this in an interview, deliver this structured response:

> *I implement a queue-based architecture using the decoupled Producer-Consumer pattern.*
>
> *First, our stateless web servers act as Producers. When an event or heavy task arrives—like an order placement or video transcoding job—the API validates input, persists the task as a message into a durable broker like RabbitMQ or BullMQ, and immediately responds with a `202 Accepted` to the client in under 15 milliseconds.*
>
> *Second, independent worker pods act as Consumers. To ensure reliability, we configure explicit Acknowledgment (ACK) mode. A message is only removed from the queue after the worker finishes processing. If a worker pod crashes mid-execution, the queue detects the unacknowledged lease timeout and automatically reassigns the message to a healthy worker.*
>
> *Third, to prevent backpressure bottlenecks where workers run out of memory, we tune the consumer `prefetchCount` so each worker only buffers what it can process immediately.*
>
> *Finally, because networks can deliver duplicate messages, all consumer logic is strictly idempotent, and failed poison pills are diverted to a Dead-Letter Queue after 3 retries.*

### 1. The Prefetch Count (Backpressure Control)
- **Without Prefetch Limit:** Worker 1 connects and immediately pulls 5,000 heavy video encoding tasks into its local RAM buffer. Worker 1 runs out of memory (OOM) and crashes, while Worker 2 sits idle with 0 tasks!
- **With Prefetch Count = 5:** Worker 1 pulls 5 tasks. It only receives the 6th task *after* it sends an `ACK` for the 1st. Work is distributed evenly across all consumers.


## Root Causes & Solutions Matrix

| Queue Challenge | Risk | Architectural Remedy |
| :--- | :--- | :--- |
| **Worker Crash Mid-Task** | Message lost permanently if broker used auto-ack. | Use **Manual ACK**: broker only deletes message after explicit worker confirmation. |
| **Poison Pill Message** | Malformed message crashes worker, requeues, crashes worker again in infinite loop. | **Dead-Letter Queue (DLQ)**: Divert message to DLQ after 3 failed attempts. |
| **Traffic Spike / Backlog** | 100,000 messages accumulate; latency grows to hours. | **Kubernetes KEDA**: Autoscale worker pods from 3 to 30 based on queue depth. |
| **Duplicate Delivery** | Network drops ACK packet; broker redelivers message. | Make consumer handler **idempotent** using a processed message ID table in DB. |


## Practical Debugging Commands & Code

### 1. RabbitMQ Consumer with Manual Acknowledgment & Prefetch (Node.js)
```typescript
import amqp from 'amqplib';

export async function startOrderConsumer() {
  const connection = await amqp.connect(process.env.RABBITMQ_URL || 'amqp://localhost');
  const channel = await connection.createChannel();

  const queue = 'order_processing';
  await channel.assertQueue(queue, { durable: true });

  // 1. Backpressure Control: Only pull 5 messages concurrently per worker pod
  channel.prefetch(5);

  console.log(`[QUEUE] Worker listening on ${queue} with prefetch 5...`);

  // 2. Consume messages with manual acknowledgment (noAck: false)
  channel.consume(
    queue,
    async (msg) => {
      if (!msg) return;

      const payload = JSON.parse(msg.content.toString());
      const messageId = msg.properties.messageId;

      try {
        // Idempotency check: verify message has not already been processed
        const alreadyProcessed = await checkIfProcessed(messageId);
        if (alreadyProcessed) {
          channel.ack(msg); // Duplicate message: ACK and discard
          return;
        }

        // Execute task
        await processOrder(payload);

        // Record message as processed
        await recordProcessedMessage(messageId);

        // 3. Explicit ACK: Message is now safely removed from queue
        channel.ack(msg);
      } catch (error) {
        console.error(`[QUEUE_ERROR] Processing failed for message ${messageId}:`, error);

        // If retries exhausted, send to DLQ (requeue: false)
        const retryCount = (msg.properties.headers?.['x-retry-count'] || 0) + 1;
        if (retryCount >= 3) {
          channel.nack(msg, false, false); // Route to Dead Letter Exchange
        } else {
          channel.nack(msg, false, true);  // Requeue for retry
        }
      }
    },
    { noAck: false } // NEVER use noAck: true in production!
  );
}
```


## Prevention & Senior Best Practices

1. **Autoscale Workers on Queue Lag, Not CPU:** Use KEDA to monitor RabbitMQ queue depth or AWS SQS `ApproximateNumberOfMessagesVisible`. Scaling on CPU is flawed because I/O-bound workers can be backlog-saturated at 20% CPU.
2. **Never Enable `noAck: true` in Production:** Auto-acknowledging messages deletes them from the broker the millisecond they are delivered, guaranteeing permanent data loss whenever a worker crashes.
3. **Persist Message Broker Storage to Disk:** Ensure RabbitMQ queues and messages are marked `durable: true` and `persistent: true` so unexpected broker restarts do not lose pending tasks.
