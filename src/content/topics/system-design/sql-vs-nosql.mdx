## TL;DR

- **SQL (Relational)**: Structured data, strict schemas, ACID compliance, complex JOINs. Scales vertically. Great for financial data and complex relationships. (PostgreSQL, MySQL).
- **NoSQL (Non-Relational)**: Unstructured/semi-structured data, flexible schemas, eventual consistency. Scales horizontally easily. Great for massive scale, fast iterations, and simple queries. (MongoDB, DynamoDB, Cassandra).

## Mental Model

| Feature | SQL (RDBMS) | NoSQL |
| :--- | :--- | :--- |
| **Data Structure** | Tables with rows and strict columns | JSON Documents, Key-Value, Graphs, Wide-Column |
| **Schema** | Rigid (Must ALTER TABLE to change) | Dynamic (Add new fields on the fly) |
| **Scaling** | Vertical (Bigger CPU/RAM on one server) | Horizontal (Add more cheap servers) |
| **Relationships** | Excellent (Foreign Keys, JOINs) | Poor (Requires denormalization or app-level joins) |
| **Integrity** | ACID guarantees | BASE (Eventually Consistent) |

## Types of NoSQL Databases

1. **Document Stores** (MongoDB, CouchDB): Stores data as JSON-like documents. Great for general-purpose apps and CMS systems.
2. **Key-Value Stores** (Redis, Memcached): Simple dictionary mapping a string key to a blob of data. Extremely fast. Used for caching and session management.
3. **Wide-Column Stores** (Cassandra, HBase): Optimized for massive write throughput and distributed storage. Used for IoT telemetry and time-series data.
4. **Graph Databases** (Neo4j): Stores data as Nodes and Edges. Used for social networks, recommendation engines, and fraud detection.

## Interview Questions

### If NoSQL scales horizontally so easily, why do we still use SQL?
Because NoSQL sacrifices **Data Integrity** and **Flexibility of Queries**. 
In SQL, you can ask the database *any* question using a JOIN, even if you didn't plan for it. In NoSQL (especially DynamoDB/Cassandra), you must know your exact access patterns before you design the database, because you cannot easily join data later. 

### Can SQL databases scale horizontally?
Yes, but it is notoriously difficult. You must implement **Database Sharding**, which breaks ACID guarantees across shards and requires complex routing logic. NoSQL databases are designed with sharding built-in from day one.

## Common Gotchas

*   **Using MongoDB just because it's "schema-less"**: If your data actually *is* highly relational (e.g., Users have Posts, Posts have Comments, Comments have Likes), using NoSQL will force you to manually write complex join logic in your application code, completely defeating the purpose.

## Remember

> Pick SQL by default. You probably aren't operating at a scale that necessitates NoSQL. Only switch to NoSQL if you have specific needs: extreme write throughput (Cassandra), flexible schemas (Mongo), or sub-millisecond caching (Redis).
