## TL;DR

Microservices architecture structures an application as a collection of loosely coupled, independently deployable services. Each service is centered around a specific business capability (e.g., Billing, Inventory, Users) and owns its own database.

## Mental Model

```mermaid
flowchart TD
    subgraph Monolith [Monolith (Single DB, Single Deployment)]
        MonoApp["Web App\n(Users + Orders + Billing)"]
        MonoDB[("Database")]
        MonoApp --> MonoDB
    end
    
    subgraph Microservices [Microservices (Independent)]
        Gateway{"API Gateway"}
        
        S1["User Service\n(Node.js)"]
        S2["Order Service\n(Go)"]
        S3["Billing Service\n(Java)"]
        
        DB1[("User DB")]
        DB2[("Order DB")]
        DB3[("Billing DB")]
        
        Gateway --> S1 & S2 & S3
        S1 --> DB1
        S2 --> DB2
        S3 --> DB3
    end
```

## Pros and Cons

### Pros
- **Independent Scaling**: If the Billing service is experiencing heavy load, you can spin up 10 more Billing servers without scaling the rest of the application.
- **Tech Agnostic**: Teams can choose the best language and database for their specific service (e.g., Go for high throughput, Python for ML).
- **Blast Radius**: If the Inventory service crashes, the User service stays online.

### Cons
- **Operational Complexity**: Deploying and monitoring 50 microservices is infinitely harder than deploying 1 monolith. Requires Kubernetes, tracing, and advanced CI/CD.
- **Data Consistency**: Because each service owns its own database, simple SQL `JOIN`s are no longer possible. You must use distributed transactions (Saga pattern) or eventual consistency (Event sourcing).
- **Network Latency**: In-memory function calls are replaced by slow network HTTP/gRPC calls between services.

## Interview Questions

### How do microservices communicate?
1. **Synchronous**: REST APIs or gRPC. (Wait for a response). Used for direct queries.
2. **Asynchronous**: Message Queues (RabbitMQ) or Event Streams (Kafka). Used for decoupled, event-driven architecture (e.g., "User created" event published, Welcome Email service reacts to it).

### What is the "Database per Service" pattern?
A strict rule in microservices that one service cannot directly query another service's database. If the Order Service needs User data, it must make an API call to the User Service. This ensures loose coupling and allows the User Service to change its DB schema without breaking the Order Service.

## Common Gotchas

*   **The Distributed Monolith**: Taking a monolithic application and simply splitting the code onto different servers without actually decoupling the databases or deployment processes. You get all the drawbacks of microservices with none of the benefits.

## Remember

> You don't *start* with Microservices. You start with a Monolith and extract microservices only when team size or scaling bottlenecks force you to. Microservices solve organizational problems, not technical ones.
