## TL;DR

Go does not have `try/catch` exceptions. Instead, errors are just normal values returned as the last argument of a function. You must explicitly check if the error is `nil` before proceeding.

## Mental Model

```mermaid
flowchart TD
    Call["res, err := doWork()"]
    
    Call --> Check{"err != nil?"}
    
    Check -->|Yes (Error)| Handle["Handle Error\n(Log, Retry, or Return)"]
    Check -->|No (Success)| Proceed["Use 'res' safely"]
```

## Example

```go
package main

import (
	"errors"
	"fmt"
)

// Function returns the result AND an error
func divide(a, b int) (int, error) {
	if b == 0 {
		return 0, errors.New("cannot divide by zero")
	}
	return a / b, nil
}

func main() {
	result, err := divide(10, 0)
	
	// Explicitly check for the error
	if err != nil {
		fmt.Println("Failed:", err)
		return
	}
	
	fmt.Println("Result:", result)
}
```

## The `error` Interface

In Go, `error` is just a simple built-in interface. Any type that implements an `Error() string` method is an error.

```go
type error interface {
	Error() string
}
```

Because it's just an interface, you can create powerful custom error structs that contain HTTP status codes, trace IDs, or retry logic.

## Wrapping Errors (`%w`)

When an error occurs deep in your application, you should wrap it with context as you pass it up the call stack.

```go
func fetchUser() error {
    err := db.Query()
    if err != nil {
        // %w wraps the original error, preserving its type
        return fmt.Errorf("failed to fetch user from db: %w", err) 
    }
    return nil
}
```

## Interview Questions

### What is the difference between `errors.Is` and `errors.As`?
- **`errors.Is(err, targetErr)`**: Checks if the error (or any wrapped error inside it) matches a specific pre-defined error value (like `sql.ErrNoRows`).
- **`errors.As(err, &targetStruct)`**: Checks if the error (or any wrapped error) matches a specific *type* (e.g. a custom `MyNetworkError` struct), and if so, extracts it into the target variable so you can access its fields.

### Why doesn't Go use Exceptions?
Go's philosophy is that errors are not "exceptional" events; they are expected behaviors (like a network timeout or file not found). Forcing developers to handle them as normal values ensures code is explicit, readable, and doesn't have hidden "goto" logic (unwinding the stack during an exception).

## Common Gotchas

*   **Shadowing `err`**: Be careful when declaring variables in block scopes (like `if err := ...`). You might accidentally shadow an outer `err` variable, leading to unexpected behavior.

## Remember

> `if err != nil` is a feature, not a bug. Embrace the explicit control flow.
