## Problem Statement

Given an integer `n`, return an array `ans` of length `n + 1` such that for each `i` (`0 <= i <= n`), `ans[i]` is the **number of 1's** in the binary representation of `i`.

**Example 1:**
```text
Input: n = 2
Output: [0,1,1]
Explanation:
0 --> 0   (0 set bits)
1 --> 1   (1 set bit)
2 --> 10  (1 set bit)
```

**Example 2:**
```text
Input: n = 5
Output: [0,1,1,2,1,2]
Explanation:
0 --> 0    (0 set bits)
1 --> 1    (1 set bit)
2 --> 10   (1 set bit)
3 --> 11   (2 set bits)
4 --> 100  (1 set bit)
5 --> 101  (2 set bits)
```

**Constraints:**
- `0 <= n <= 10^5`

**Follow up:**
- It is straightforward to solve in $O(N \log N)$ by counting bits for each number individually. Can you solve it in linear time $O(N)$ in a single pass?
- Can you do it without using built-in functions?


## Why Brute Force is Suboptimal ($O(N \log N)$)

The naive solution iterates from `0` to `n` and calls Brian Kernighan’s algorithm on each number:
```javascript
// O(N log N) time
for (let i = 0; i <= n; i++) {
    ans[i] = hammingWeight(i);
}
```
Because computing set bits for a number up to $N$ takes $O(\log N)$ bit operations, repeating this for all $N$ numbers results in $O(N \log N)$ time.

Can we achieve **$O(N)$ linear time**? Yes! Instead of calculating the set bits of each number from scratch, we use **Dynamic Programming (DP)** to build on previously solved subproblems.


## Approach: Dynamic Programming Transitions

There are two primary $O(N)$ recurrence relations. Both are elegant and frequently discussed in interviews:

### Method 1: Right-Shift + LSB (Most Intuitive)
Consider the number `5` in binary: `1 0 1`.
If we chop off its rightmost bit using right shift (`5 >> 1`), we get `2` (`1 0`).
Notice that:
$$\text{bits}(5) = \text{bits}(2) + \text{last bit of } 5$$

Since $2 < 5$, `dp[2]` was already computed earlier in our array!
- To drop the last bit: `i >> 1`
- To check if the dropped bit was a 1: `i & 1`

$$\text{dp}[i] = \text{dp}[i \gg 1] + (i \ \& \ 1)$$

### Method 2: Brian Kernighan Recurrence
From LeetCode #191, we know `i & (i - 1)` deletes the lowest set bit from `i`.
Therefore, `i` has **exactly one more set bit** than `i & (i - 1)`:
$$\text{dp}[i] = \text{dp}[i \ \& \ (i - 1)] + 1$$

Because `i & (i - 1)` is strictly less than `i`, `dp[i & (i - 1)]` has already been calculated!

## Solution

### Method 1: Right-Shift + LSB (Recommended)

```javascript
/**
 * @param {number} n
 * @return {number[]}
 */
var countBits = function(n) {
    const dp = new Array(n + 1).fill(0);
    
    // dp[0] = 0 is the base case
    for (let i = 1; i <= n; i++) {
        // dp[i] = dp[i / 2] + (1 if odd else 0)
        dp[i] = dp[i >> 1] + (i & 1);
    }
    
    return dp;
};
```

### Method 2: Brian Kernighan Transition

```javascript
/**
 * @param {number} n
 * @return {number[]}
 */
var countBitsKernighan = function(n) {
    const dp = new Array(n + 1).fill(0);
    
    for (let i = 1; i <= n; i++) {
        // dp[i] has 1 more set bit than i with its lowest set bit cleared
        dp[i] = dp[i & (i - 1)] + 1;
    }
    
    return dp;
};
```


## Complexity Analysis

- **Time Complexity:** $O(N)$
  - We iterate from `1` to `n` in a single pass.
  - In each iteration, we perform simple $O(1)$ bitwise operations (`>>`, `&`) and array lookups.
  - Total time is strictly linear $O(N)$, outperforming the $O(N \log N)$ brute force approach.
- **Space Complexity:** $O(1)$ auxiliary space
  - Beyond the output array `dp` of size $n + 1$ (which is required by the problem return signature), only constant extra variables are used.
